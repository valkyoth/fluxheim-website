PHP-FPM Bridge

Available since v1.3.1 via the php-fpm Cargo feature. The PHP-FPM bridge connects Fluxheim to a running PHP-FPM pool using the FastCGI protocol. It supports WordPress-style front-controller applications with strict script resolution and bounded request/response handling.

bash — build with PHP-FPM support
cargo build --release --no-default-features \
  --features profile-web-server,php-fpm,acme-client
fluxheim.toml — WordPress front-controller
[[vhosts]]
name = "wordpress"
hosts = ["blog.example.com"]

[vhosts.tls]
enabled = true

[vhosts.web]
root = "/srv/sites/wordpress"
index_files = ["index.php", "index.html"]
deny_dotfiles = true

[vhosts.php]
enabled = true
runtime = "php-fpm"
root = "/srv/sites/wordpress"
index = "index.php"
allowed_extensions = ["php"]

[vhosts.php.fpm]
socket = "/run/php/php8.2-fpm.sock"

How PHP routing works

  • Requests for existing .php files are routed directly to PHP-FPM
  • Requests for non-existent files fall back to the front controller (index.php)
  • Static assets (.css, .js, images) are served directly without touching PHP-FPM
  • Script resolution is strict — only files within the configured PHP root are passed to FPM

fluxheim-acme Companion

Released in v1.3.2. fluxheim-acme is a standalone companion binary for managing ACME certificate renewal and reload operations outside of the main gateway process. It is designed for container and external service-manager deployments where the gateway does not own the renewal lifecycle.

bash — fluxheim-acme operations
# Check ACME certificate status
fluxheim-acme status

# Trigger a certificate renewal (respects ACME rate limits)
fluxheim-acme renew

# Signal the gateway to reload certificates via Unix socket
fluxheim-acme reload

# Run as a daemon for automatic periodic renewal
fluxheim-acme daemon --check-interval 12h

The ACME reload socket lets fluxheim-acme signal the running gateway to pick up freshly issued certificates without a full restart. Configure the socket path in your [server] block.

fluxheim.toml — ACME reload socket
[server]
acme_reload_socket = "/run/fluxheim/acme-reload.sock"

fluxheim-config-tester

Released in v1.3.2. fluxheim-config-tester is a standalone binary that validates a Fluxheim config file without starting the gateway. Useful in CI pipelines and container entrypoints where config errors should be caught before being applied to a running service.

bash — validate config before apply
# Validate a config file — exits 0 on success, non-zero on error
fluxheim-config-tester --config /etc/fluxheim/fluxheim.toml

# Use in a container entrypoint before starting the gateway
fluxheim-config-tester --config /etc/fluxheim/fluxheim.toml && \
  exec fluxheim --config /etc/fluxheim/fluxheim.toml

Zero-Retention Privacy Mode

The privacy-mode feature compiles Fluxheim without any caching or metrics functionality, enforcing zero log retention at the build level. This is suitable for privacy-sensitive deployments where no request data should be stored or exported.

bash — zero-retention privacy build
# privacy-mode is compile-time incompatible with cache and metrics
# Always use --no-default-features (default build includes cache)
cargo build --release --no-default-features \
  --features profile-privacy

# Validate the feature combination before building
scripts/validate-features.sh proxy,web,tls-rustls,privacy-mode

What privacy-mode enforces

  • No cache module compiled — caching is impossible at the binary level
  • No metrics module compiled — no Prometheus or OTLP export
  • Access logs may be disabled in the config
  • Compile-time guarantee: no data is stored, no external telemetry is exported

Admin API

The admin control-plane exposes a local HTTP API for health checks, config reload, cache purge, and status queries. It defaults to loopback-only and requires a bearer token on non-loopback listeners.

bash — admin API endpoints
ADMIN="http://127.0.0.1:9090"
TOKEN="your-admin-token"

# Health check (authenticated)
curl -H "Authorization: Bearer $TOKEN" $ADMIN/_fluxheim/health

# Live config reload
curl -X POST -H "Authorization: Bearer $TOKEN" $ADMIN/_fluxheim/reload

# Cache purge by selected identity
curl -X POST -H "Authorization: Bearer $TOKEN" \
  "$ADMIN/_fluxheim/cache/purge?host=example.com&path=/app.js"

# Aggregate cache status
curl -H "Authorization: Bearer $TOKEN" \
  "$ADMIN/_fluxheim/cache/status"

# Cache warm through the CLI
fluxheim --config /etc/fluxheim/fluxheim.toml cache-warm \
  --host example.com --path /app.js

WASM Extensibility

Planned — v1.6

Fluxheim's WASM extensibility layer is planned for the 1.6 release. It will support nginx-Lua-style request/response hooks and VCL-like cache policy hooks through WebAssembly modules.

  • Compile-time opt-in wasm feature
  • Hook points: request received, upstream response, cache policy, response send
  • Shared memory model between WASM modules and the host
  • Sandboxed execution with bounded resource limits

WAF Architecture

Planned — future

A Web Application Firewall module is documented in the architecture but not enabled in the current stable builds. It is planned as a compile-time optional module with rule-based request filtering, rate limiting per IP/path/method, and configurable block/log/challenge responses.

Load Balancer

The load-balancer feature adds Pingora's load-balancing module and health checks to the proxy runtime. It is opt-in and available today via profile-load-balancer or profile-load-balancer-edge.

fluxheim.toml — upstream pool with health checks
[[upstreams]]
name = "app-pool"
strategy = "round-robin"   # or "least-conn", "random"

[[upstreams.backends]]
address = "10.0.0.1:3000"
weight = 1

[[upstreams.backends]]
address = "10.0.0.2:3000"
weight = 1

[upstreams.health_check]
path = "/health"
interval_secs = 5
timeout_secs = 2
healthy_threshold = 2
unhealthy_threshold = 3

[[vhosts.routes]]
name = "app"
path_prefix = "/"
[vhosts.routes.proxy]
upstreams = ["127.0.0.1:3000"]
upstream_pool = "app-pool"

Security — Dependency & Vulnerability Policy

Fluxheim enforces a strict dependency policy across all releases:

  • Pinned Rust stable toolchain via rust-toolchain.toml
  • Checked-in Cargo.lock for reproducible builds
  • GitHub CI with CodeQL scanning on all pushes
  • cargo deny for license and dependency policy enforcement
  • cargo audit for advisory checks against the RustSec database
  • Rootless Podman smoke tests before every container release

Report vulnerabilities privately via SECURITY.md.
